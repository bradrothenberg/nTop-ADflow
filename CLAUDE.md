# nTop to ADflow

Run ADflow (MDO Lab) on geometry generated by an nTop notebook, and get adjoint gradients
of the forces with respect to nTop-style geometry parameters.

**Read this whole file before running anything.** Several failure modes in this pipeline
produce a plausible wrong number rather than an error. They are marked SILENT below and
listed in full in `docs/GOTCHAS.md`.

## What works today, and what does not

| Capability | State |
|---|---|
| nTop notebook to a triangulated surface, headless | works (`ntop_adflow/ntop.py`) |
| Closed slender body to a structured ADflow mesh | works, validated end to end |
| Euler solve, forces and moments | works, validated to 2e-9 against reference |
| Adjoint gradients w.r.t. body length and section scales | works, verified |
| Cancellation diagnostic K on every gradient | works, and it matters. Read it. |
| **Wing, fin, tail, full aircraft** | **NOT IMPLEMENTED.** Needs overset. See below. |
| **Actual optimization** | **BLOCKED:** pyOptSparse is not installed |
| RANS / viscous drag | not set up; Euler only |

The surface generator makes a body of revolution with elliptical cross-sections: a
fuselage, a store, a nacelle centrebody. It cannot make a wing. ADflow needs a structured
or overset mesh, and there is no automatic structured mesher for a general nTop part. For
lifting surfaces you must build one near-body mesh per component and assemble an overset
grid; the recipe is in `docs/GOTCHAS.md` under "Overset assembly" and the reference is
`MACH-Aero/tutorial/overset/mesh/run_pyhyp.py`.

Do not claim this repo runs a full aircraft. It does not yet.

## Workflow

### 1. Define the case

Copy `cases/agardc_body.yaml` and edit it. Required fields are validated on load, and two
of them have no safe default:

- `flow.liftindex` — **2 means lift along y, 3 means lift along z.** ADflow defaults to 2.
  nTop aircraft geometry is normally z-up, so it needs 3. With the wrong value the number
  reported as CL is **side force**. This is SILENT. `config.py` refuses to run without it.
- `geometry.ratio` and `geometry.ratio_at_x` — see step 2.

### 2. Build the surface (Windows)

```bash
uv run --with pyyaml --with numpy --with scipy --with pyvista python scripts/build_case.py cases/<name>.yaml
```

Add `--export` to run the notebook through `ntopcl` first, instead of using an existing
`geometry.surface_file`.

This measures the body profile, builds the cubed-sphere surface, and writes
`work/<name>/` with `profile.npz`, `surface.fmt`, `case.json` and `health.json`.

**Check the printed health numbers.** All three must hold:

```
shared edge gap    0.00e+00     patches must coincide exactly
min edge length    > 0          no collapsed cell
ratio cross-check  within a few percent of the notebook's Y/Z scale inputs
```

SILENT trap in the measurement: **do not measure the body radius near z = 0.** On a
wing-body geometry the wing is also there, so the slice reads the wing span instead of the
body radius. `geometry.side: bottom` reads the bottom of a narrow centreplane band, which
is clear of the wing. And `geometry.ratio_at_x` must be a station **forward of the wing
root leading edge** — at mid-body on AGARD-C the check returns 2.16 instead of 1.234. No
code can pick that station for you.

### 3. Push and extrude

```bash
bash scripts/push.sh <name>
ssh 192.168.20.10 "cd ~/ntop_adflow_cases/<name> && ./extrude.sh"
```

**Read the extrusion output.** Bad cells must be **0** and minimum quality about **0.9**.
A segfault, or a metric printed as `0.180+309`, means the SURFACE topology is wrong, not
the solver. The usual cause is an odd `surface.n`, which puts a grid point on a pole.

### 4. Solve

```bash
ssh 192.168.20.10 "cd ~/ntop_adflow_cases/<name> && ./solve.sh"
```

Writes `results.json`. About 133 s on 8 ranks for a 369k-cell mesh at L2 1e-12.

SILENT trap: **an inviscid closed body must produce zero drag.** At a subcritical Mach
number the fore and aft pressure forces cancel exactly. Any CD you get is discretization
error — on the reference case it is 0.0423, which is 100 percent error. Never quote it as
drag and never minimize it. Use CL, CMY or a target pressure distribution instead.

### 5. Gradients

Smoke test first. Same code path, loose tolerance, one variable, no finite difference,
about 2 minutes:

```bash
ssh 192.168.20.10 "cd ~/ntop_adflow_cases/<name> && ./smoke.sh"
```

Then the full run: 1 solve, 3 adjoints, 6 solves for the verification. About 21 minutes.

```bash
ssh 192.168.20.10 "cd ~/ntop_adflow_cases/<name> && ./gradients.sh"
```

Writes `gradients.json` and `gradients.npz`.

## How the gradients work

```
dJ/dp = (dJ/dX_surf) . (dX_surf/dp)
```

The **flow term** is ADflow's discrete adjoint: one adjoint solve per function, and the
cost does **not** grow with the number of design variables. The **geometry term** is pure
geometry: two generator calls per design variable and zero CFD solves. A full finite
difference needs two flow solves per variable, so the two costs cross at two design
variables.

Design variables, which mirror the nTop fuselage handles:

| Variable | Meaning | nTop handle |
|---|---|---|
| `L` | body length | FUSE-Len |
| `Sy` | horizontal radius scale | FUSE-YScale |
| `Sz` | vertical radius scale | FUSE-ZScale |

Node correspondence across a perturbation is exact by construction: node `(patch, i, j)`
always maps to the same cubed-sphere direction. That is what makes `dX_surf/dp` well
defined node by node, and the generator is exactly linear in all three variables, so the
central difference on it is exact. `tests/test_surface.py` asserts both.

### The two things that will bite you

**SILENT and severe: the surface derivative needs BOTH seeds.**
`computeJacobianVectorProductBwd(funcsBar=..., xSDeriv=True)` alone returns the
**frozen-flow partial**, which ignores how the pressure field responds to the shape change.
The total needs `resBar = -getAdjoint(f)` in the same call, after `solveAdjoint`. Measured:
the partial was wrong by up to 17 times and wrong in **sign** for 2 of 9 pairs, yet under a
width scaling it reproduced CL and CD to **nine digits**. It looks right. `gradients.py`
prints both so the gap stays visible; if the two are close, you have dropped the seed.

**Read K before trusting a gradient.** `gradients.py` prints, for every gradient,

```
K = sum|c_i| / |sum c_i|      c_i = (dJ/dX_i).(dX_i/dp)
```

K measures how much the projection relies on cancellation. On the validated 32x32 case:

| K | Outcome |
|---|---|
| <= 63 | all four pairs verified to better than 2 percent |
| >= 376 | all five pairs failed by 5 to 32 percent |
| in between | nothing landed there |

Rank correlation between K and the error was 0.983 over four decades. K costs nothing —
both terms are already in hand — so it flags a bad gradient with no extra solve and no
finite difference. Values above `gradients.k_warn` are flagged in the log.

K is a reliable **ordering**, not a quantitative law: a linear `K x 1 percent` model
over-predicts by one to two orders at large K, because the nodal errors partly cancel
among themselves.

The underlying cause is understood: the adjoint surface derivative is accurate to about
1 percent everywhere on the body, including the closures, and cancellation amplifies that
into the projected gradient. Refining the surface reduces the 1 percent, and the large-K
gradients improve fastest.

### If a new case shows the same 5-32 percent gap

These causes are already ruled out on the reference case. Do not re-derive them; the
evidence is in `docs/VALIDATION.md`.

| Suspect | Verdict |
|---|---|
| Geometry term | exact to 1e-10 |
| Chain assembly, node mapping, MPI reduction | exact to 3e-7 (rigid-translation test) |
| Mesh warp derivative | consistent to 1.2e-3 |
| Finite-difference noise | ruled out: FD moves < 1.6 percent over 30x in h |
| Duplicated-node double counting | ruled out: dividing by multiplicity is worse |
| Adjoint inaccurate at the body closures | ruled out: closure agrees to 0.6-1.2 percent |

Run the diagnostics in this order:

```bash
# 1. is the chain itself right? known answer: zero for CL and CD
mpirun -np 8 --mca pml ob1 --mca btl self,vader,tcp python diagnostics/rigid_check.py
# 2. is the finite difference the noisy side, or the adjoint?
RB_DV=L RB_STEPS=1e-2,3e-2 mpirun -np 8 --mca pml ob1 --mca btl self,vader,tcp \
    python diagnostics/step_study.py
```

A flat step study means the finite difference is converged and the gap belongs to the
adjoint side, which points back at K.

Also remember what a finite difference can prove: it confirms the derivative of the
**discrete** functional. It cannot confirm the physics, because both sides share one mesh
and inherit the same discretization error.

## Adding a new geometry

1. Discover the notebook's input schema instead of guessing it:
   ```python
   from ntop_adflow import ntop
   ntop.template("path/to/model.ntop", outdir="work/tmp")
   ```
2. Copy `cases/agardc_body.yaml`, set `geometry.notebook` and `geometry.inputs`.
3. Set `x_nose` and `x_tail` to the actual body ends, and `measure_from`/`measure_to`
   strictly inside them. A slice exactly at a closed tip returns too few points.
4. Choose `ratio_at_x` at a station clear of every lifting surface, and cross-check the
   printed ratio against the notebook's Y/Z scale inputs.
5. Set `flow.liftindex` deliberately.
6. Build, push, extrude, and check bad cells is 0 before spending a solve.

## What is missing, in priority order

1. **pyOptSparse.** The only missing MACH-Aero package, so no optimization can run yet.
   Not on PyPI:
   `pip install "pyoptsparse @ git+https://github.com/mdolab/pyoptsparse.git"`.
   That gives SLSQP, which is enough for a few design variables.
2. **Surface refinement.** Set `surface.n: 64`. The spurious CD must fall toward zero, and
   the large-K gradients should improve fastest. Both are the same fix.
3. **Cross-check against ADflow's own design-variable path.** Wrap the body in a pyGeo FFD
   box, add one local shape variable, and compare `evalFunctionsSens` against a finite
   difference on it. The chain here is validated to 3e-7 by the rigid-translation test, but
   that test is a translation-invariance identity, so it cannot rule out every misuse of
   `xSDeriv`. This closes the last gap.
4. **Overset for lifting surfaces.** One near-body pyHyp mesh per component, then
   `combineGrids` from cgnsutilities, then `symmZero("y")`, then `simpleOCart` for the
   Cartesian background, then combine near and far field. ADflow then needs
   `surfaceFamilyGroups` mapping the component families to `wall`.
5. **RANS**, after overset works. That is what finally gives a physically meaningful drag.
